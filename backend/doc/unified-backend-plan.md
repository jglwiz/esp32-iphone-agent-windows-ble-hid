# 统一控制与画面后端实施计划

状态：已实施并完成验收与清理。日期：2026-11-02。逐项证据、备份位置及已知边界见 [实施记录](implementation-status.md)。以下保留迁移前的设计要求和实施顺序；历史现状不代表当前部署。

## 目标与边界

以 8892 为唯一客户端业务入口，提供 ESP32 BLE HID 控制及手机截图。停用 8890 旧 USB 控制后端，迁移客户端后不保留旧动作路由兼容层。保留独立 UxPlay 与 8891 取帧进程，8891 仅作为回环内部依赖。API 重启不得中断投屏。

本轮提供最新 JPEG 截图，不新增连续视频播放、录屏或 WebSocket。现有 8893 校准页是供手机访问的专用监听，保持现有令牌及访问范围，不把业务 API 暴露到局域网；“唯一入口”指客户端控制和取图入口。

纳入 ESP32 重置／重启 API，明确排除刷写固件、恢复出厂设置、清除配对。本轮讨论属于架构评审，以下目录、模块接口和新增 API 是设计目标，不代表已实现或授权立即执行设备操作。

## 已确认现状

- [service.py](../src/iphone_backend/service.py) 是 BLE 控制 FastAPI，监听 127.0.0.1:8892，提供 POST /action，串口由单一 worker 持有。
- [frame_capture.py](../src/iphone_backend/airplay/frames.py) 从 127.0.0.1:8891/frame 读取原子快照 v1，并验证帧标识、时间、JPEG 和大小。
- 实际 Windows 取帧源码在父工作区 upstream-windows/server/hidagent/capture_worker.py，使用标准库 ThreadingHTTPServer，并非第二个 FastAPI；screen_pipe.py 负责接收管道与画面。该目录是独立项目，不能随旧控制代码一并删除。
- [服务管理](service-management.md) 已有管理进程及受保护的 restart API；迁移应沿用现有进程交接和释放串口机制。
- 8890 的当前进程、实际部署路径、自启动项及剩余调用方尚待实施时核实。此前列出的 esp32-iphone-agent/server/hidagent/app.py 是旧方案源码，不足以证明运行中的 8890 来自该目录。
- upstream-windows/server/hidagent/capture_client.py 的 Screen._ensure_worker 会在帧源缺失时启动 capture_worker。停用旧后端必须接替这项启动职责；已有 8891 进程存活不能证明电脑重启后仍能使用。

## 项目组织调整

以 esp32-iphone-agent-windows-ble-hid 为唯一主项目。backend server 是最上层，下面只有两个核心子模块：esp32 与 airplay。API、配置、日志和主控管理属于 backend server 的公共职责，不再引入平级的 input、capture、device 等业务子系统。

用户授权按“新建子文件夹 → 复制 → 调整 → 验证切换 → 最后删除旧文件”重新组织后端文件。统一新目录选为主项目根下 backend/，不再在 pc/ 内原地重构。目标目录如下（拟新增）：

迁移流程的硬约束：所有新代码、修复、测试、启动脚本及开发文档均在 backend/ 内编写。测试验收完成前，旧代码和旧目录结构保持原样，只读取或复制，不修改、不移动、不删除，也不把旧入口改成转发脚本。当前计划文件的修订是本次规划工作的例外，不代表实施阶段可以修改旧代码。后文的客户端迁移、文档更新与旧服务退役均遵守此先后顺序。

```text
backend/
  pyproject.toml           # 可安装 Python 包、依赖与启动命令
  src/
   iphone_backend/
    __init__.py
    __main__.py            # python -m iphone_backend 统一启动
    app.py                 # FastAPI 组装、路由及请求校验
    manager.py             # 主控入口、API 子进程交接、跨进程管理请求
    orchestration.py       # 动作 → 等待 → 截图、视觉定位与校准编排
    config.py              # 配置与日志基础设施可按规模拆分
    esp32/
      service.py           # 命令、设备状态、重置任务
      serial_transport.py  # 唯一串口所有者、协议及握手
    airplay/
      service.py           # 启动/状态、接收器与取帧生命周期
      frames.py            # 原子快照读取与校验
      worker.py            # 从旧项目复制、调整的取帧进程
  tests/                   # 后端自动化测试
  doc/                     # 后端模块说明及迁入的计划
.runtime/                  # 主项目现有运行数据，独立于源码目录
```

| 层级 | 职责与边界 |
|---|---|
| backend server | 对外 API、生命周期、配置、日志、管理操作准入及两个子模块的编排 |
| esp32 子模块 | 发送 HID 命令、串口发现与独占、会话/握手、设备状态、释放输入、设备重置；不直接调用 AirPlay 或管理 UxPlay |
| airplay 子模块 | 接收器与取帧进程的启动/复用、状态、原子快照与新鲜度信息；不访问 ESP32 串口 |
| backend 编排 | 组合动作与截图、视觉定位、坐标校准；分别调用两个子模块，不让子模块相互导入 |

外部调用依赖 backend API；backend 依赖两个子模块；两个子模块不反向依赖 FastAPI。设备操作与进程管理通过窄接口调用，不向路由暴露原始串口句柄或任意命令执行能力。现有 SerialWorker 中同时处理动作和截图的逻辑需逐步拆出：保留串口独占与动作串行语义，将跨模块流程放到 backend 编排层。

第一阶段（新目录开发与测试）：新建 backend/，从 pc/ 复制后端、客户端、校准及相关测试，从 upstream-windows 复制必要取帧实现与依赖，保留许可证。所有调整仅发生在 backend/，旧代码和旧结构完整保留。新文档、测试脚本和部署草案也只放 backend/。禁止新旧实例同时占用串口、8891 或同名取帧管道。开发期间可读取既有帧源，隔离测试使用模拟设备及临时资源；实机测试通过运行时交接安排，不能通过修改旧源码来让测试通过。最终源码纳入同一次迁移，不再将取帧源码整合无限期留给后续项目。

第二阶段（验收与正式切换）：在旧代码仍完整保留时，确认新包不从 pc/ 或 upstream-windows 导入代码，完成本计划规定的自动化、实机、重启和冷启动验收。测试通过后正式更新外部客户端、技能、启动项及文档入口。新 API 可先复用现有取帧实例；取帧进程切换在明确安排的停止窗口或自然冷启动进行，不为目录调整主动中断投屏。服务身份检查在过渡期显式允许已核实的旧帧源实例，最终仅接受新部署身份。尚有待验收项目时保留旧代码，不进入删除阶段。

第三阶段（最后清理旧代码）：新版本全部验收通过且正式切换成功后，按迁移清单删除已替代的旧文件，更新文档链接及 AGENTS 导航；清理后再做新入口冒烟。删除不是开发或排错步骤。不删除仍被运行进程引用的源码或依赖，不按整个 pc/ 或 upstream-windows 目录一刀切；固件、独立实验、历史证据及其他项目文件按清单保留。删除前校验绝对路径范围，并保留可恢复的版本或备份。计划在开发阶段复制至 backend/doc/ 维护，旧计划保留到最终清理；本次仍更新现有文件。

### Python 包入口与运行路径（架构评审第 4 项）

- backend/pyproject.toml 声明唯一包 iphone_backend；安装到指定 Python 环境后统一以 python -m iphone_backend 启动。子进程使用同一 Python 可执行文件及明确的模块入口，包内使用包限定或相对导入，不依赖 sys.path 临时拼接或当前工作目录。
- backend 配置层统一解析并向子模块/子进程传递绝对配置与数据路径。部署配置显式指定 runtime_dir，初次迁移沿用主项目现有 .runtime；保留 service/calibration-profile.json 等原有数据的相对布局。禁止各模块通过 __file__.parents 推断数据根目录。
- 管理锁、IPC 身份信息、持久任务、校准与日志共用已确定的数据根；生产和测试使用不同数据目录。API 与主控必须使用同一个实例配置，防止搬目录后生成第二把管理锁。
- AirPlay 的 HIDAGENT_DATA、UxPlay 配置和可执行文件位置逐项核实并显式传入，不假定它们与控制器 .runtime 同目录。源码迁移不同时隐式移动运行数据。
- 校准网页等只读资源打包在包内，通过包资源接口读取；可写数据不得写入安装包目录。迁移回归覆盖不同 cwd、含空格路径、包安装后启动，以及相同配置读取同一份校准和锁文件。

### 完整任务并发边界（架构评审第 1 项）

Backend 编排层独占完整控制任务，从移动、取图判断到点击和结果确认完成后才释放；其他输入任务排队，重置/重启/校准按既有忙碌规则拒绝或调度。独占由任务状态/预约实现，不在等待画面期间长期持有管理互斥锁。ESP32 子模块独立串行执行命令并持续维护心跳，取帧延迟不能饿死设备会话。

只读 GET /frame、状态和日志可与动作并行，不进入控制任务队列；当前任务也可反复取帧。并行帧可能来自操作前或中间状态，作为动作结果必须另行满足 settled_at 与新鲜度要求。取消后先完成输入释放和任务收尾，再允许下一控制任务；结果未知的输入不重放。

## 目标进程、线程与串口内部服务

以下是目标运行模型，不是当前进程/线程数量的实测结果。两个源码子模块不对应两个独立进程：ESP32 服务位于 API 进程内；AirPlay 在 API 内提供访问接口，在主控内提供生命周期管理，在独立进程内执行持续取帧。

| 进程 | 职责 | 主要线程 |
|---|---|---|
| Backend 主控 Python 进程 | 统一启动、IPC 管理请求、API 监督与交接、协调取帧启动 | 1 个主线程，运行事件循环 |
| Backend API Python 进程 | FastAPI、完整任务编排、ESP32 服务、异步画面访问 | 1 个 API 主线程事件循环 + 1 个固定编排线程 + 1 个串口工作线程 |
| AirPlay 取帧 Python 进程 | 读取 UxPlay 输出、发布原子快照、提供内部 8891 接口 | 1 个异步服务主线程 + 1 个持续画面读取线程 |
| UxPlay 外部运行时 | 接收并解码手机投屏 | 由 UxPlay 管理，不纳入 Python 线程预算 |

原始预算是 3 个 Python 进程、5 个主要线程，外加 UxPlay 外部运行时。实现中 API 增加一个固定视觉编排线程，避免同步视觉算法阻塞 API 事件循环；因此当前为 6 个固定主要线程，具体职责见 [架构说明](architecture.md)。Windows venv 启动器、UxPlay 包装器/引擎可能产生额外系统进程；框架线程池和图像库可能增加线程，因此不以系统总数恰好等于上述预算作为验收。API 保持单 worker，禁用 reload 和多 worker，避免复制串口所有者。

```text
Backend 主控进程（主线程事件循环）
├── Backend API 进程
│   ├── 主线程：API、异步 frame 读取
│   ├── 固定编排线程：完整视觉与输入任务
│   └── ESP32 串口工作线程：队列 → 协议/心跳 → 串口
└── AirPlay 取帧进程
    ├── 主线程：内部快照 HTTP 接口
    └── 读取线程：UxPlay 管道 → 转换画面 → 发布最新快照

UxPlay 外部运行时：独立常驻，向取帧进程提供画面
```

### ESP32 串口作为进程内服务

- esp32/service.py 暴露命令提交、状态及设备重置接口；它是进程内服务对象，没有独立 HTTP 监听或额外进程。Backend 通过有界命令队列提交工作，通过 Future 异步等待结果，不在 API 事件循环中调用阻塞的 Future.result()。
- 唯一串口工作线程负责打开、读写和关闭串口，以及握手、心跳、释放输入和重置。路由、主控、其他线程和直接串口脚本都不得绕过该所有者。状态读取使用线程安全的快照，不通过第二个串口连接查询。
- 工作线程在空闲等待以及执行命令期间都负责设备心跳，使用有界串口读写与响应等待。等待 AirPlay、视觉计算、界面稳定和 HTTP 响应属于 Backend 编排，不占用串口工作线程；不得持有串口队列执行权等待截图。
- 命令队列项携带任务标识、截止时间及取消信号。Backend 持有完整任务预约，ESP32 仅执行属于当前预约的输入命令；心跳不受该预约阻塞。取消、超时和关闭时明确完成或拒绝未执行 Future，结果未知的命令不重发。
- 设备重置由同一个线程执行，并更新 boot_id 和连接绑定。API 优雅退出时通过控制消息请求释放输入与关闭串口，等待工作线程结束后才能交接给新 API；仅靠守护线程随进程退出不算完成清理。

### AirPlay 并发与线程迁移

API 内的 AirPlay 访问采用异步 HTTP，不为每次截图创建读取线程。取帧进程通过唯一持续读取线程处理命名管道及画面转换，以短临界区发布不可变快照；HTTP 主线程读取同一快照的 JPEG、时间和 ID，避免跨帧拼接。读取管道不持有快照锁，HTTP 不等待下一帧才能响应。

现有 capture_worker 使用 ThreadingHTTPServer，会按请求创建线程。为实现上述目标，将其内部服务改为异步 HTTP 实现，仍保留 8891 快照协议和回环限制；这是内部适配器，不增加第二个对外 FastAPI 业务应用。已有 service.py 为截图启动临时线程的逻辑在编排迁移时移除，心跳转由串口线程独立维持。

主控的进程等待和 IPC、API 的截图读取都不能阻塞各自事件循环。耗时视觉计算和阻塞文件操作若需卸载，使用有界执行器，不按请求无限创建线程；额外线程在实现记录中注明。校准页 8893 以 API 进程内异步监听为目标，保留令牌隔离，相关改动纳入校准回归；若暂保留现有线程实现，明确记录为迁移期例外。

API 重启仅重建 API 进程及串口会话，保持取帧进程和 UxPlay。主控统一安排取帧启动，API 中的 AirPlay 客户端只有读取与委托管理能力，不能自行生成第二个接收器。

### 1a. 主控进程管理取帧启动（P1 修正）

backend 主控管理进程是唯一应用启动入口，调用 airplay 子模块启动或复用取帧服务；FastAPI 通过受控本机 IPC 委托同一管理功能，不自行再实现一套进程启动逻辑。取帧独立进程不是独立的用户启动步骤。过渡期可复用已核实的 upstream-windows 运行实例；最终从新包启动取帧进程。记录 Python 可执行文件、依赖环境、AIRPLAY_NAME、HIDAGENT_DATA、取帧端口、UxPlay 路径及日志位置；不依赖 8890 导入或启动副作用。

启动前检查 8891 的服务身份及 owner。正确实例存在则复用；端口由其他服务占用则明确失败，不抢占。帧源不存在时只启动一个进程，处理并发启动竞争并有界等待健康检查；日志不得泄露凭据。仅在 UxPlay 不存在时沿用帧源的启动逻辑，禁止为恢复截图默认重启既有接收器。

统一启动时先有界尝试确保帧源就绪，再启动 API 子进程；帧源启动失败也继续启动 API，以便查询降级状态和手动重试。仅配置主控入口的开机启动项，与旧启动项去重。POST /screen/start 使用相同启动功能，返回可查询任务；已有正确实例时成功复用，进程就绪与手机已连接/已有帧分别报告。IPC 需要身份校验、有界超时和请求去重；主控不可用时管理请求明确返回不可用。

进程关系：backend 主控管理进程持有启动协调锁，API 与取帧作为不同工作进程运行；API 内 esp32 worker 独占串口。API restart 只重启 API 子进程；取帧和 UxPlay 保持运行。主控恢复时识别并复用既有实例，不重复启动或强杀。退出主控也不隐式关闭投屏；整体关闭策略明确记录，本轮不增加停止/重启 AirPlay API。

主控恢复协议（架构评审第 2 项）：主控在固定 runtime 中持有唯一锁和实例登记，API 身份包括 PID、进程创建时间、instance_id、配置身份与版本。主控重启后先认证并核对既有 API，再通过 IPC 重新登记监督关系；仅端口可达不算接管成功。身份未知或版本不兼容时拒绝接管，报告需受控退出旧 API 的恢复步骤，不强杀或启动第二个串口所有者。

接管后的 API 不再是当前主控创建的子进程，监督不能只依赖 Popen.wait 和退出码。管理协议记录重启请求及清理成功结果，主控同时确认旧 API 进程真正退出、端口与串口所有权释放后才启动替代实例；缺少清理证据时停止自动交接，报告状态。API 在主控失联时继续允许正常只读/控制能力，但依赖主控的启动及重启请求返回不可用，不能接受后无人执行。

取帧启动任务由主控保存，POST /screen/start 返回 request_id，可通过 GET /screen/start/{request_id} 查询；任务和去重记录存入固定 runtime。API 重启不会丢失任务；主控恢复时依据服务身份和实际状态完成对账，不盲目再次启动。用故障注入验证主控先死、API 先死、IPC 中断与重启交接中断的行为。

冷启动验收必须覆盖无需 8890 的完整启动。先以模拟进程及临时端口验证编排，再在自然冷启动或明确安排的服务停止窗口验证真实环境；不为测试主动停止当前投屏。未完成真实冷启动时记录待验收，不以进程仍存活代替通过。

### 2. 在 8892 增加画面接口

保留现有 POST /action 及响应字段；将画面路由与串口执行逻辑分离，复用帧校验逻辑，避免在 service.py 中继续堆叠取帧实现。

接口约定：

| 接口 | 行为 |
|---|---|
| GET /frame | 返回 JPEG，保留真实 X-Frame-Time、X-Frame-Id、X-Frame-Snapshot-Version，添加 Cache-Control: no-store |
| GET /screen/status | 返回取帧服务可达性、画面可用性、帧时间与年龄，区别无画面和依赖故障 |
| GET /health | 保留现有字段；增加画面依赖状态，画面离线不伪装成整个控制服务退出 |

无帧返回 204；帧源不可达或超时返回 503；元数据或 JPEG 不合法返回 502。读取设有界超时、大小限制，禁用环境代理；不接受用户提供的任意上游 URL。保留快照原始时间，静止画面不能通过改写时间伪装成新帧。

快照新鲜度契约（P2 修正）：

- GET /frame 读取帧源当前提供的最新合法快照，不等待手机产生新帧。即使年龄超过 5 秒，只要帧源仍提供该快照，也返回 200 和原始帧时间/ID；若帧源返回 204，则返回 204，不用本地历史缓存冒充当前画面。
- GET /screen/status 明确提供 reachable、frame_available、frame_time、age_seconds、freshness 及状态观测时间。无帧时帧字段为 null；freshness 区分 fresh、stale_or_unknown、unavailable、invalid。年龄不超过 5 秒且满足既有时钟容差时为 fresh；超过 5 秒不能断言是静止还是卡住，使用 stale_or_unknown。未来时间超出既有 1 秒容差视为 invalid。
- 状态与图片是两次独立观测，不承诺跨请求原子一致；取图调用者以该 JPEG 自带的帧 ID/时间判断新鲜度。
- snapshot.py 迁移地址后保留原有 5 秒新鲜度限制及报错行为。用于人工查看的最新快照与用于动作证据的新鲜截图不能混用。
- 动作后的截图继续使用 FrameCapture.capture 的截止时间、新鲜度和 settled_at 判定。GET /frame 复用底层读取/校验，不直接套用会等待新鲜帧的 capture；截图失败不得重新执行动作。

画面读取不进入串口动作队列，不占有串口。控制器内部仍直接调用帧源适配器，不通过 HTTP 回调自己的 /frame。现有动作后新鲜帧检查、取消、幂等与未知结果不重放语义保持一致。健康检查中的画面探测使用短超时或缓存，避免取帧故障拖住重启检查。

产出：客户端可仅通过 8892 完成动作及独立取图。

### 2a. ESP32 设备管理与重置 API

新增 GET /device/status、POST /device/reset、GET /device/reset/{request_id}。reset 表示重启当前绑定 ESP32，不刷固件、不擦除配对或配置。API 只接受绑定设备及请求标识，不接受任意串口或复位脚本。

现有 bridge.py 只确认使用 CH343 串口、DTR/RTS 默认置 false，尚未确认可靠复位机制。实现前核实板级复位接线、串口控制线能力及当前固件协议：优先使用已支持的重启命令，否则验证可用的串口硬件复位序列；不能假定开关串口就是设备复位，也不能进入下载模式。当前硬件/固件不支持时报告能力不支持，作为待解决项，不为完成 API 偷换成后端重启或刷固件。

执行契约：

- 复用管理 API 的回环校验和 token 认证。请求包含 request_id、expected_instance_id、expected_device_id 与 expected_boot_id，防止旧页面或重试请求重置错误实例。
- 与动作提交、校准和后端重启共享管理准入锁。有在途动作、排队任务、校准或重启时返回 409，不隐式取消后重放。接受重置后暂停新输入任务，返回 202 及任务查询位置。
- 由 esp32 唯一串口 worker 执行释放输入、单次复位和重新握手；不由路由另开串口。故障恢复时允许在无在途任务的前提下重置，释放失败必须记录为未确认，不能声称已释放。
- 观察新 boot_id、稳定设备身份及重新建立的串口会话，分别报告 device_rebooted 与 BLE/HID readiness。重启确认不等于手机已恢复可操作；完成结果明确区分已重启待 BLE 恢复、可用、失败和结果未知。
- 复位后旧会话、定位证据及校准的运行时有效性失效，重新建立连接绑定；按现有规则重新验证后才能接受依赖校准的点击。保留配置和历史证据，不自动清除配对。
- 请求按设备和旧 boot_id 去重；同 ID 不重复发复位，参数不一致则冲突。任务记录在发复位前落盘；进程中断后以记录和实际 boot_id 恢复状态，不自动重发结果未知的复位。BLE 恢复超时和握手失败均不自动重复重置。

### 2b. Backend 公共管理功能

保留 GET /health、POST /admin/restart 的既有客户端契约，增加设备重置与取帧启动的互斥/任务状态。backend restart 与 device reset 是不同管理操作；前者交接 API 进程，后者重启 ESP32。

健康状态分层（架构评审第 3 项）：分别报告 Backend 存活/可服务、ESP32 readiness/fault、AirPlay readiness/fault 和主控可达性。主控 wait_ready 以 API 身份和服务就绪为准，不再将单个设备 fault 当作 Backend 启动失败并退出监督。ESP32 缺失或故障时，仍提供帧、日志、状态及符合设备身份条件的恢复管理操作；输入接口明确报告不可用。AirPlay 离线时保留 API，依赖画面的动作按其前置条件失败。现有健康字段保持兼容，并增加分模块状态。

新增受保护的 GET /system/logs，按 backend、esp32、airplay 固定来源查询日志，支持有界条数或游标，不接受任意文件路径。日志关联 request_id、服务实例、设备 boot_id 和帧 ID；隐藏 token 等凭据。日志读取失败不影响动作执行。API 文档按 esp32、airplay、system 分组，不强行为分组修改既有 /action、/frame 等路径。

按项目约定，主代理编写实现与测试；GPT-6.1 Terra / Medium 子代理执行自动化测试及实机操作，主代理审查证据。离线测试使用模拟串口、模拟帧源与临时端口，不接触实机服务。

必须覆盖：

- 静止画面超过 5 秒时，最新快照接口仍可返回帧源提供的合法图片，状态为 stale_or_unknown；snapshot.py 及动作后截图继续拒绝不符合各自新鲜度要求的帧。帧源 204 时不得回退到旧图，图片时间与 ID 不变造。
- 不启动 8890 的独立取帧冷启动；已有实例复用、身份不匹配拒绝、重复启动竞争、启动失败和超时均有证据。覆盖 Python 环境及工作目录与调用目录不同的情况。

- device reset 覆盖忙碌拒绝、认证、设备/boot_id 不匹配、请求去重、唯一串口所有权、释放失败、握手超时、BLE 延迟恢复，以及任务中断后不重复复位。单独验证新 boot_id 和校准状态失效，不能以 202 或串口重新打开作为重启成功。
- 实机设备重置后确认设备身份与 boot_id、BLE 就绪状态、投屏连续性，再按既有规则验证定位后执行无外部副作用的动作。复位机制未经验证时报告阻塞，不以模拟结果替代。
- 日志 API 验证来源白名单、分页/大小限制、认证和凭据隐藏；管理操作日志能关联任务结果。
- 同时取图和执行动作时，串口保持单一所有者；动作幂等、取消和取帧失败不重放仍通过现有回归。
- 完整视觉任务等待截图期间，其他输入任务不能插入，GET /frame 仍可并行响应，ESP32 心跳持续；取消和重置不会绕过完整任务准入。
- 记录目标进程身份与主要线程职责；验证只有串口所有者线程触碰串口，关闭时释放并结束该线程。并发取帧不会逐请求增加专用线程，快照元数据保持原子一致；有界执行器容量及超载行为可观测。
- 验证截图延迟、视觉计算及慢日志读取不阻塞 API 响应或串口心跳；迁移内部异步 HTTP 和校准监听后，快照 v1 及校准回归仍通过。线程池或外部库线程数量单独记录，不将“5 个主要线程”误作系统总线程数承诺。
- 主控崩溃后重新接管存活 API，不重复打开串口；身份不符拒绝接管；跨主控实例的 API 重启需确认清理及旧进程退出；取帧启动任务在 API/主控重启后仍可查询。
- 无 ESP32 或握手故障启动时，Backend 及主控仍正常提供画面、日志和状态；符合前提的恢复操作可执行，设备故障不使主控永久停止监督。

## 回退与完成标准

部署前保留 8892 版本及配置记录。新接口故障时回退 8892 代码与对应客户端，保留 UxPlay/8891；不将重启 8890 作为 BLE 方案回退步骤。串口释放失败按现有管理器策略停住并报告，不强制重放输入。

实施完成必须同时满足：8890 停用；客户端只依赖 8892 获取控制与画面；新 backend/ 包可独立部署 API 与帧源；主控统一管理启动并通过故障恢复验收；8891 可脱离 8890 冷启动；完整任务独占与并行取帧、健康分层、包入口和固定运行路径通过回归；设备重置及日志 API 通过验收；真实点击与画面闭环通过；API 重启不破坏投屏；旧文件按清单完成最后清理；文档与实际部署一致。

三个阶段分别记录复制调整、验证切换、旧文件清理的证据。真实冷启动、实机复位或取帧切换未验证时明确列为待验收，不提前删除仍被使用的旧文件。创建或修订此计划不代表任何实施事项已经完成。
