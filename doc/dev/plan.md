# PC 串口 → ESP32 BLE HID → iPhone：探索与实施计划

日期：2026-10-30。状态：**P0、P1 完成**，固件 0.2.0 的实际键盘输入、退格、鼠标移动与点击通过。实际进度见 [验证记录](validation.md)。P2–P4 尚未整体完成，本文中尚未实现或测试的部分仍为候选设计。

## 目标与范围

在独立子项目中实现以下链路：PC 通过串口发送动作命令；ESP32 发布一个包含键盘和鼠标的 BLE HID 设备；iPhone 配对后接收键盘、相对鼠标移动、点击、拖动和滚轮输入。首阶段提供命令行控制，不依赖 iPhone 自定义 App。

控制链路不依赖 Wi-Fi。后续视觉控制可复用现有 AirPlay 取帧，其网络要求独立于串口与 BLE。第一阶段不实现 GUI、模型调用、多手机切换、多点触控、任意 Unicode 文本注入或未经验证的绝对坐标触控。

规划轮只创建说明与计划；用户随后授权实施 P1，已创建 firmware/、pc/、tests/ 和 scripts/。后续阶段按验收结果推进。

## 技术选择

### 1. 当前采用独立 NimBLE-Arduino；保留初始选型依据

实施调整：内置 BLE 库出现重复 UUID 特征漏注册，局部修复后手机仍未执行输入。当前 0.2.0 已改用固定版本 NimBLE-Arduino 2.3.8 做对照；本节保留初始选择理由，当前构建与验收以 [使用说明](../user/usage.md)和 [验证记录](validation.md) 为准。

理由是本地已具备工具链与对应头文件，可直接维护一个复合 HID 服务和统一的连接、配对、输入状态。首轮固定版本，使用该版本 S3 默认的 NimBLE 栈（已核对本地 sdkconfig）；不同时引入多个第三方键盘、鼠标库，避免重复初始化 BLE 和服务生命周期冲突。

官方 [BLEHIDDevice 源码](https://github.com/espressif/arduino-esp32/blob/3.3.12/libraries/BLE/src/BLEHIDDevice.cpp)提供报告映射、输入/输出报告和服务构建能力。实际加密状态、通知订阅与配对回调仍需编译和实机核验，不能将头文件存在等同于 iPhone 兼容。

备用方案是固定发行版本的 ESP-IDF 官方 [BLE HID 示例](https://github.com/espressif/esp-idf/tree/master/examples/bluetooth/bluedroid/ble/ble_hid_device_demo)，其中包含鼠标、键盘等报告，目标列表包含 ESP32-S3。只有首选路线出现明确的 API 或兼容性阻塞时再做最小对照，不同时维护两套固件；实施时记录具体版本或提交，不长期依赖 master。

### 2. PC 侧首选 Python + pyserial

当前已实现同步 CLI 和串口客户端，支持状态、键盘、鼠标操作；request 等待响应时解析异步事件，并为长动作发送心跳。一次只允许一个动作在途，尚无独立读线程、常驻控制进程或完整动作队列。后续若增加多入口控制，再以统一串口所有权和有界队列避免动作、心跳争抢；不能假定当前脚本会在任意空闲等待期间自动续租。

现有 Python 3.11 环境可用于探索，正式依赖在本项目独立声明，不靠导入旧项目的私有模块才能运行。版本在实际安装和冒烟后固定。未来如复制上游 MIT 代码，保留原版权与许可证。

### 3. 串口首选板载 CH343 → UART0

建议起步 115200 baud、8N1，固件显式使用 UART0 对象（Arduino Serial0）；不依赖随 USB 编译选项变化的 Serial 别名。原生 USB CDC 可作为诊断或后续替代，首轮不同时支持两条命令入口。相关行为参考 [乐鑫 UART 文档](https://docs.espressif.com/projects/arduino-esp32/en/latest/api/serial.html)和 [USB 编译选项](https://docs.espressif.com/projects/arduino-esp32/en/latest/guides/tools_menu.html)。

PC 打开串口时控制 DTR/RTS，验证打开/关闭是否触发自动复位；收到带启动标识的握手后才发送命令。开机 ROM 日志和结构化协议不能混淆：PC 在握手前忽略非协议行，运行日志使用单独的事件类型。禁止在新固件注册 USB 键盘、鼠标接口，PC 只应接收串口通信。

COM4 是本次观察值，不能硬编码为永久设备地址；未来按 VID/PID、设备序列号与 USB 父设备关系识别，并允许显式指定端口。出现多个候选时报告候选，不自动选择第一个。微雪 [板卡说明](https://docs.waveshare.net/ESP32-S3-DEV-KIT-N8R8/)解释了 CH334 Hub、CH343 与原生 USB 的连接关系。

## BLE HID 设计要点

- 一个 HID Service（0x1812），一个复合 Report Map；建议键盘 Report ID 1、鼠标 Report ID 2。键盘先使用标准修饰键加 6 键数组；鼠标先使用按钮、相对 X/Y 和垂直滚轮。水平滚动与媒体键后续独立验证。
- 每个输入报告建立匹配的 Report Reference 和通知特征；明确 Report ID 位于描述符/报告引用的编码规则，不能把 USB 报告缓冲区原样当作 BLE payload。Boot Protocol 如实现，必须与 Report Protocol 一致，不能只放置占位特征。
- 状态分别报告 BLE connected、bonded、encrypted、keyboard_subscribed、mouse_subscribed；键盘动作与鼠标动作按各自就绪条件检查，拒绝尚未就绪的动作。
- 配对信息保存在 NVS；记录协商后的安全状态与失败原因。配对期间的身份验证交互按实际 IO 能力实现，不声称具备没有实现的显示或键盘能力。断开后恢复广播；订阅恢复后先发全释放报告，再接受输入。
- 第一版仅面向一个手机连接。提供显式清除配对操作；更新 Report Map 后，必要时同时清除手机旧配对与设备 bond，重新做完整验证。
- iPhone 鼠标需要打开辅助触控，可从“设置 → 辅助功能 → 触控 → 辅助触控 → 设备 → 蓝牙设备”连接。路径与指针行为依据 [Apple 官方说明](https://support.apple.com/zh-cn/111775)。键盘输入另需验证实际输入法和硬件键盘布局。

## 串口协议 v1 草案

选择按行 JSON（UTF-8，换行分帧），暂定每帧最多 512 字节，超长行丢弃至下一换行并报错。第一版负载不高，可读性比压缩带宽更有价值；暂不引入二进制协议。

以下请求格式已实现；操作表仍保留候选项，当前固件没有 keyboard.text_ascii 或 bond.clear，文本转换在 PC 端完成：

```json
{"v":1,"session":"pc-session-1","id":12,"op":"mouse.move","dx":20,"dy":-10}
```

| 类别 | 建议操作 | 含义 |
| --- | --- | --- |
| 握手和状态 | hello、status、ping | 获取协议版本、固件版本、boot_id、能力和 BLE 各层状态；建立当前 PC 会话。 |
| 鼠标 | mouse.move、mouse.click、mouse.down、mouse.up、mouse.scroll | 相对移动、单击、按下、释放、垂直滚动；参数范围受限，超范围明确报错或按已定义规则拆分。 |
| 键盘 | keyboard.tap、keyboard.down、keyboard.up、keyboard.text_ascii | 以 USB HID usage 与修饰键为底层语义；文本限定已定义的英文布局，非 ASCII 明确拒绝。 |
| 恢复 | release_all、cancel | 高优先级终止排队/当前可中断动作并释放；不能排在长动作后等待。 |
| 配对维护 | bond.clear | 显式操作，清除 bond 并进入重新配对流程。 |

每条响应关联 session、id、boot_id。区分 accepted（解析和排队成功）、sent（本动作所需报告已完成本地提交）和 error；BLE 通知发送不等于 iOS 已执行动作，业务成功仍需观察手机。可能部分执行的错误返回 partial/unknown 等明确状态，禁止伪装为完整成功。

同一 boot_id、session 内保存有界的在途状态和最近完成结果，相同 id 与相同请求重发时不重复执行；相同 id 对应不同请求时拒绝。PC 记录缓存有效范围。超时首先查询状态；跨重启、换会话或缓存过期的点击、按键、拖动不自动重放，返回“结果未知”。本设计不承诺跨掉电的 exactly-once。

当前固件只保留一个活跃动作，新动作冲突返回 busy；完整工作队列仍为候选。串口解析和 BLE 回调保持响应。长移动拆为有界增量，按可配置节奏提交，不能复制旧 USB 的 8 ms 时序后就假定 BLE 等效；在通知拥塞时背压或报错，不无界堆积。大文本拆分为有界片段。

按键/按钮维护显式状态。候选心跳间隔 500 ms、失联阈值 2 s，实测后调整；串口链路不能总能检测物理拔线，因此依赖会话租约。租约过期、cancel 或连接故障时取消队列、清空本地按下状态；BLE 仍连着则发送释放，BLE 已断则在重新就绪后补发全释放。长按由活跃会话续租，不能因动作执行而阻塞心跳。

## 实施顺序与验收

### P0：硬件与构建基线

1. 沿用用户已确认的现有 ESP32-S3，以及既有记录中的 iPhone 17e；使用昨天验证过的芯片、Flash 与 PSRAM 配置。实机验证时补录 iOS、辅助触控和输入法设置；刷写前重新识别串口并核对芯片身份，不再把硬件选型作为待用户回答的问题。
2. 设置独立构建输出与运行数据目录，固定 core 3.3.12、板型与 Flash/PSRAM 配置；核对 UART0、CDC、USB 模式，不能照搬旧 TinyUSB HID 配置。
3. 实施阶段首次覆盖固件前备份“当前”Flash 并记录校验值和恢复步骤。已有 ../.backups/esp32-s3-before-hid.bin 是更早的原镜像，不能视为当前 USB HID 固件的备份。

验收：构建工具能定位现有依赖；明确目标板和端口；备份与恢复资料齐全。用户授权实施后已完成，见验证记录。

### P1：最小串口与 BLE 端到端验证

1. 新固件只建立串口握手、状态和复合键鼠 HID；启动时不自动发输入。
2. iPhone 首次配对后，记录连接、加密、各报告订阅。先在明确聚焦的测试文本框发送一个字母和退格，再发送可观察的鼠标移动和点击；每步由串口显式触发。
3. 若无效，按广播 → 配对/加密 → 描述读取 → CCCD 订阅 → 报告编码 → 手机效果逐层排查。必要时做键盘单独、鼠标单独的对照构建，最终仍验收复合设备。

验收：同一个 BLE 设备同时支持实际文字输入和指针移动、点击；保存日志及手机操作前后证据。仅有 connected、订阅或 notify 成功不能通过。AirPlay 看不到指针时直接观察手机或用画面变化确认，不能仅凭镜像缺少指针判失败。

### P2：协议与故障恢复

1. 实现完整 v1 协议、CLI、参数限制、动作队列、重复请求处理、会话租约与释放逻辑。
2. 测试半包/粘包、非法 JSON、超长行、错序响应、重复 id、回执丢失、BLE 未就绪和队列背压。断线/复位测试要覆盖动作部分执行后回执缺失。
3. 按住键或鼠标时关闭 PC 客户端、断开串口、关闭手机蓝牙，分别检查释放与重连；拖动中途失败不得自动重演。

验收：重复请求不会多点一次或多输入一次；超时不会盲目重试有副作用动作；会话失联后按候选 2 s 阈值释放，允许一个报告调度周期误差。断开 BLE 后重新连接不会保留旧按下状态或重放历史队列。

### P3：动作覆盖与稳定性

1. 实测 ASCII、Shift 组合、方向键、退格、鼠标单击/按住/释放、拖动和垂直滚动；记录 iOS 映射和不支持项。
2. 连续执行至少 100 次可核验按键及点击测试；分别做 10 次 BLE 断开重连、10 次板子重启恢复、30 分钟混合输入。记录失败次数、恢复耗时和串口往返延迟；手机可见延迟单独测量。
3. 对锁屏、解锁、越距、休眠和手机重新开蓝牙记录实际结果；不能把解锁状态通过推广成所有状态可用。

验收：支持的动作无漏释放、无重复执行；恢复测试不需反复清除配对。若部分恢复需手动连接，明确记为限制，不宣称自动恢复通过。测试数字是最低验收目标，不是已实现指标。

### P4：接入现有视觉控制（基础链路通过后）

1. 设计 SerialDevice 适配器，保留 send/connected/links 等上层需要的语义，替换 TCP 传输。将连接与输入可用状态分开，不能仅串口打开就让上层执行动作。
2. 复用现有常驻取帧服务的接口，不重启 UxPlay；新项目的配置、日志与校准结果独立保存。
3. 为 BLE 重新校准相对位移、速度和拖动节奏；旧 USB 校准文件不可直接沿用。home 指针归位与 iPhone Home 系统动作必须命名区分。
4. 验证多个屏幕位置点击、滚动及输入，并在每次动作后检查画面。中文输入和更复杂手势另行定义实现与验收。

验收：通过新项目从画面选择目标、经串口/BLE 操作并由新画面确认成功；坐标误差按固定测试点记录。停止新控制客户端不会停止既有取帧服务。

## 尚待确定与结论

目前没有阻止开始最小实现的架构问题。沿用昨天已测试、用户本次再次确认的 ESP32-S3，硬件选型已确定。iOS 版本可在实机验证时补录；本机 BLE 复合键鼠与配对已通过基础实测；重连表现和最合适的报告节奏仍需进一步验证。

这条路线的本机端到端基础输入已于 2026-10-30 验证通过。后续可基于当前 0.2.0 固件推进 P2 的故障恢复验收、P3 稳定性与 P4 视觉控制集成；本轮不把这些阶段视为已完成。

## 后续优化建议（2026-10-31，待实施）

当前证据支持继续沿用 0.2.0 与 NimBLE-Arduino 2.3.8，暂无依据更换 BLE 库或提高报告频率。优先解决可靠性与操作便利性，以下是讨论形成的候选顺序，不表示已实现或已通过验收。

1. **故障恢复先行**：在按住键或拖动期间，分别模拟客户端终止、串口断开和 BLE 断开；补测锁屏、解锁与板子重启。必须确认手机端无残留按下状态、无重复输入；恢复前后的截图和串口事件分别保存。收到 lease_expired 或重新 hello 后报告清零，不足以单独证明手机端超时释放有效。
2. **常驻 PC 控制进程**：统一持有串口、维护心跳和就绪状态；恢复后先释放输入并确认报告就绪，再接受新动作，不重放结果未知的历史动作。具体接口和队列策略在实施时确定。
3. **视觉校准**：复用 AirPlay 截图，为 BLE 单独测定位移比例、移动节奏和多位置点击误差，不套用旧 USB 校准。当前拖动和滚轮通过单轮测试，不代表坐标映射已经可靠。
4. **输入覆盖**：验证 Shift、标点、快捷键及输入法组合态；保留 ASCII/布局边界，不能以键位转换单元测试代替手机端字符验收。

性能评估应区分串口往返和手机可见延迟。2026-10-30 的 108 次状态查询中位数约 62 ms，含客户端串口读取开销；60 秒全部成功只是短时状态采样，不能代替 P3 的 30 分钟混合输入与重连测试。完整实测数据以 [验证记录](validation.md) 为准。
