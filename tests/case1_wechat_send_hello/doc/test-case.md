# 微信文件传输助手实机测试

目的：测量 Agent 通过 PC 串口 → ESP32-S3 → BLE HID 操作 iPhone 的完整流程；将子代理执行与主代理验收分开。真实发送消息，仅用于用户已授权的测试。

## 固定用例

若开始时已经在主屏幕，先打开微信作为准备，再实际执行返回主屏幕，不能把初始画面当作返回动作的证据；准备过程单独标注并保留计时。

从实际起始画面开始计时，回到 iPhone 主屏幕（App 资源库不计作主屏幕），打开微信，进入“文件传输助手”，确认并切换硬件输入法为 English (US)，验证 ASCII 输入后，发送且只发送本轮唯一的 `test_{id}`。以发送气泡出现、输入框清空、无可见失败标记作为本机发送成功证据，不声称云端送达或已读。

测试前确认手机解锁、辅助触控开启、BLE 键鼠 ready、AirPlay 可取新鲜截图。保留既有 UxPlay/取帧服务。不得使用桌面微信或其他消息接口替代手机操作。

## 职责与执行

操作模型、推理强度和分工遵循项目 [AGENTS.md](../../../AGENTS.md#iphone-实机操作分工)。主代理派发时须实际设置相应模型与推理强度，并在本轮验收记录中保存实际配置；记录工具的 `--model` 只保存标签，不会创建或切换子代理。历史记录没有显式推理强度时保持未知，不补写为 Medium。

主代理初始化 run.json，将绝对运行目录、准确消息和本用例交给用户指定模型的子代理。主代理记录派发时间，监控子代理消息及阶段截图；操作期间不同时占用串口。必要时中断子代理。未获得发送成功证据，不因子代理口头报告成功而通过。

子代理读取项目约定，保存 start 截图后开始。依次记录 home、wechat、recipient、input_method、ascii_probe、input_ready、draft、sent 阶段，截图必须来自本轮实时画面。每阶段发送简短进展给主代理。可在已确认目标的前提下合并移动、点击、取图和看图，减少工具往返；不得根据旧画面连续猜测操作。

### 必经步骤：确认英文硬件输入法

若修饰键异常，先按[已验证的分阶段修饰键顺序](../../../firmware/serial_ble_hid/doc/keyboard-modifiers.md#固定按键顺序与可复用回归)及固定`fixtures/shift_a_staged.json`复现。该诊断不能替代下面完整English (US)、`a_A-1`和清空验收，不发送诊断文本。

1. 在“文件传输助手”聚焦空输入框，调出硬件输入法选择列表（可尝试 Control+Space）。根据当前画面选择 `English (US)`；已经选中时也须留存证据。若需保持修饰键展开列表，必须在同一串口会话中完成选择并及时释放，避免租约过期。快捷键只是候选操作方法，发出成功回执不等于切换成功。
2. 保存能确认英文选中状态的 `input_method` 截图。屏幕键盘的“双/英”按钮、字母大小写或 English (US) 仅出现在列表中，都不能单独证明硬件输入法已经选中英文。
3. 在草稿中输入探测文本 `a_A-1`，不发送。保存 `ascii_probe` 截图，逐字符确认小写 a、ASCII 下划线、大写 A、ASCII 连字符和数字 1，且没有待确认的组合文本、自动替换或额外空格。若无法辨清，停止，不猜测通过。
4. 清空探测文本，保存空输入框的 `input_ready` 截图，随后输入本轮完整 `test_{id}` 并按 draft 阶段核对。清空动作须看图确认，不能假定 Cmd+A 对所有输入法有效。
5. 若无法选择英文或探测失败，至多完成一次有证据的修正与复测；仍失败则清理草稿、释放输入并记录 stop。不得继续发送、改用近似字符或无验证地粘贴。

英文切换和探测耗时计入本轮操作时长。主代理必须独立核对 input_method、ascii_probe、input_ready；缺少任一项不能判定完整用例通过。阶段记录工具只检查证据及顺序，实际画面仍需主代理验收。

发送前检查标题确为“文件传输助手”，文本逐字符等于 run.json 的 message。处理输入法组合态，确保没有额外空格、换行、大小写变化。双语输入法可能将下划线转为长横线；必须逐字符核对，必要时清空草稿、切换英文并重输，禁止将近似文本计为通过。发送后若回执或画面不确定，先观察，不盲目再次发送。目标不唯一、无法看清文本、断线或锁屏时停止并说明原因。结束释放所有输入，保留投屏运行。

## 主代理验收

主代理独立查看各阶段截图，检查确实回到主屏幕、从手机打开微信、收件人正确、英文硬件输入法已选中、ASCII 探测通过且已清空、消息精确匹配、仅一个本轮气泡、输入框清空且无失败标记。证据不足为 inconclusive；明确错误为 fail；全部符合才为 pass。

在运行目录保存 evaluation.json 和 evaluation.md：结论、逐项证据、开始/结束时刻、操作时长、主代理复核时间、动作/截图/工具调用次数（若未测量则明确写未知）、失败尝试与恢复、改进建议。run.json 的 pending_main_review 不等于结果；evaluation 文件为正式验收。

操作时长按 start 到 sent 的截图 frame_time 计算，包含中间模型判断及工具等待；不含子代理启动与读规则。派发至主代理验收结束另列为总交付时间，不混用两种计时。比较模型时统一任务、起始页面和工具，报告重试次数；单轮成功不能证明长期稳定性，也不用于宣称固定提速倍数。

## 常驻服务执行模式

使用 [PC 常驻服务](../../../pc/doc/service.md) 时，先由主代理启动服务，子代理只调用 service_client.act，禁止同时打开 Bridge 串口。run.json 记录 transport=http_service、实际模型及推理强度、service instance_id 和对照轮次。每次动作可直接返回截图，子代理应合并工具调用与图片查看。live_case.py 阶段记录方式不变。

服务保留相对位移，并新增自动视觉定位的 move_to/click_at。使用视觉绝对模式（visual_relative）时在 start 后先 move_to(250,540) 验证居中，此耗时纳入 start→sent；每次绝对动作重新获取参考，不能认为一次居中后坐标永久有效。输入法与探测要求不变；不得为了速度省略收件人、精确文本和发送后核验。capture_error不代表输入失败，只观察，不重放动作。每请求结束释放输入，多步按住操作必须放在一个有界请求内。

常驻服务模式的关键草稿编辑使用至少1500ms等待，并在发送前额外观察一次，不修改文字；两次都匹配本轮文本后才发送。若看到疑似未删前缀，先观察确认，不立即重复删除。首轮服务测试出现最终少一个 t 的失败，说明帧时间新鲜不等于文字编辑已稳定。

## 原生 HID 后端的用例执行

显式选择 `coordinate_backend=native_hid` 时，先完成当前设备/连接的 verify 与 scope 验收；不套用旧视觉后端每次重新定位和居中流程。指针动作必须位于批准区域，使用新页面截图决定目标。键盘及纯观察请求的结果可能仍标默认 visual_relative；这不表示实际调用了视觉鼠标，须按请求内的动作判断。准备起点由操作子代理自主完成，单列计时；保持文件传输助手输入为空、键盘收起，再开始实际返回桌面。
